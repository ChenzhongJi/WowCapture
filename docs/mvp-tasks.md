### 0.1 S1 实测结果（2026-11-20）

测试机：单屏 2880×1800（5.18 MP / 19.8 MB），Windows 11 26300，Release 构建，命令 `--bench-capture 40`。

| 指标 | 数值 |
|---|---|
| 冻结帧总耗时（含取 DC、建 DIB、拷贝） | min 32.3 / **P50 38.6** / P95 45.2 / max 47.7 ms |
| ├ BitBlt | 33.3 ms（**88%**） |
| └ `Marshal.Copy`（19.8MB） | 1.2 ms（3%） |
| 单位开销 | **7.44 ms/MP** |
| 外推双 4K（17.7 MP） | **≈132 ms** P50（预算 200ms，余量约 34%） |
| `CAPTUREBLT` 相对纯 `SRCCOPY` | **0.94x**（无额外开销） |

结论（直接影响实现）：

1. **预算成立，不做按屏并行抓取**。省掉一套线程与拼接逻辑，M1 的复杂度显著下降。
2. **`CAPTUREBLT` 免费，保留为默认**。它能把提示框、分层窗口一起抓进来，而在这台机器上没有可测的性能代价。
3. **瓶颈是 BitBlt（屏幕回读），不是托管拷贝**。`GC.AllocateUninitializedArray` + 单次 `Marshal.Copy` 已经够快（1.2ms），不值得再上 D3D 纹理或池化。
4. **双 4K 是线性外推，未实机验证**。M1 结束前需找一台双 4K 机器复测；若实测明显超线性，再考虑按屏并行。
5. **峰值工作集 342MB 是基准自己制造的抖动**（每轮新分配 19.8MB 连续 80 次），真实会话只持有一帧，参考价值有限。但双 4K 单帧 66MB 仍意味着 M1 要盯着"会话结束必须释放"这条（T1.9）。

### 0.2 T1.9 资源压测结果（2026-11-20）

命令 `--stress 30` / `--stress 60`，每次迭代走一遍"抓屏 → 转位图 → 裁剪 → 会话对象创建/销毁"。

| 指标 | 30 次 | 60 次 | 判定 |
|---|---|---|---|
| 单次耗时 | 43.5 ms | 42.9 ms | 稳定 |
| GDI 对象 | 1 → 1（Δ0） | 1 → 1（Δ0） | 无 DC/DIB 泄漏 |
| USER 对象 | 10 → 10（Δ0） | 10 → 10（Δ0） | 无窗口/句柄泄漏 |
| 托管内存 | 0.6 → 20.4 MB（Δ19.8MB） | 同（Δ19.8MB） | 只留一帧 |
| 私有内存 | Δ79.6 MB | Δ81.5 MB | **高水位，非泄漏** |

关键判据：**迭代翻倍而增量不翻倍**。私有内存涨到 ~80MB 看起来可疑，但 30 次与 60 次的增量几乎相同
（差 2MB），说明是 .NET 堆与 WPF 的一次性高水位，不是每次迭代漏一点。真正的泄漏会让 60 次变成 ~160MB。

> 教训：只看"内存涨了"没有意义，必须做**迭代翻倍对比**才能下结论（陷阱清单第 22 条）。

## 6. 陷阱清单（血泪预埋）

1. **别用 `AllowsTransparency=true`** 做遮罩。会掉软件渲染、多屏大面积下卡顿撕裂。用 D1 的冻结帧方案。
2. **别忘了 `SetWindowPos` 设物理像素**。只改 WPF `Width/Height` 默认是 DIP，高缩放下得到 1.5 倍大的窗口。
3. **负坐标**。副屏在主屏左边时 `X` 是负数，所有 `Rectangle` 运算都要按 `X + Width` 算右边界，别写成 `X + Width == right` 就直接 `Contains`。
4. **`CAPTUREBLT`** 能抓分层窗口（菜单、提示框），但会带来闪烁；只在需要时开。
5. **黑图不是异常**。DRM/游戏/部分 UWP 会给纯黑，必须检测并回退，否则用户会拿到一张全黑图还以为自己操作错了。
6. **剪贴板 alpha**。`Clipboard.SetImage` 在部分应用里会丢透明或变黑底，务必同时写 `PNG` 格式（D6）。
7. **`RenderTargetBitmap` 的 DPI**。默认 96，在 150% 屏上渲染出的像素尺寸会不对，要么按屏幕 DPI 渲染，要么在导出后校验尺寸。
8. **遮罩抢焦点**。不调用 `SetForegroundWindow` 会收不到键盘事件（Esc、方向键全部失灵），调用了又要防止它出现在 `Alt+Tab` 里（`WS_EX_TOOLWINDOW`）。
9. **预处理鼠标坐标**。WPF 事件是 DIP，物理像素转换只在一个地方做，否则会散落 20 处 `* dpiScale`。
10. **文字工具的输入法**。直接在 `OnRender` 里画字符会丢 IME 组合状态，必须用真正的 `TextBox` 覆盖层。
11. **撤销不要存位图快照**。双 4K 一张 66MB，20 步就 1.3GB。存标注列表。
12. **热键注册失败要说话**。静默失败是自用工具变成"今天不好使"的头号原因。
13. **`File.Replace` 要求目标存在**。首次写配置时文件不存在会抛异常，先判断。
14. **托盘 `NotifyIcon` 用完必须 `Dispose`**，否则退出后图标残留在通知区域，要等鼠标划过才消失。
15. **别在 UI 线程做 `BitBlt`**。66MB 拷贝会卡住动画，也会让遮罩显示延迟叠加。
16. **`[LibraryImport]` 不会自动补 `W` 后缀**。`PostMessage` 在 user32 里只有 `PostMessageW/A`，
    写成 `[LibraryImport("user32.dll")] PostMessage` 编译完全正常、运行时才抛 `EntryPointNotFoundException`。
    要么写 `EntryPoint = "PostMessageW"`，要么退回 `DllImport` + `CharSet.Unicode`。
    （实测踩过一次：诊断模式直接卡死，因为异常被第 17 条吞掉。）
17. **全局异常处理器不能只写 `Handled = true`**。吞掉 UI 异常会让进程带着坏状态常驻——
    热键还占着、托盘还在，但功能已经不可用，表现为"没反应也不退出"，最难排查。
    正确做法：全局处理器一律按致命处理（记日志 + 退出），可恢复的异常在调用点接住
    （例如遮罩会话用 try/catch 关窗口后继续常驻）。
18. **`GetDpiForMonitor` 与 PMv2 的信任问题**。微软文档提示 PMv2 进程不宜用它推导窗口尺寸；
    读缩放比例在实践中可用，但要像 `--diagnose` 那样用 shcore 的 `GetScaleFactorForMonitor`
    交叉验证一次，不一致就说明这条路不可信。
19. **WinForms 与 WPF 混用时全局 using 会打架**。`UseWindowsForms` 会把 `System.Drawing`、
    `System.Windows.Forms` 塞进全局 using，于是 `Pen`/`Point`/`Brush`/`KeyEventArgs` 全部二义。
    用 `<Using Remove="System.Drawing" />` 摘掉全局引入，只让托盘那一个文件自己 `using`。
20. **`Clipboard.SetDataObject(data, copy, retryTimes, retryDelay)` 这个重载不存在**（命名参数直接编译失败）。
    剪贴板被占用（`0x800401D0`）是常态，得自己写重试循环；`copy: true` 时 WPF 会立即刷新，
    但传进去的 `MemoryStream` 不要在设置完之前释放。
21. **别用缩略图肉眼判断渲染是否成功**。遮罩到底画没画出来，要用像素断言：
    选区角点必须是边框色、选区外亮度必须明显低于原图。我第一次就是看缩略图看错了，
    白折腾一轮去查"窗口没显示"，其实它一直在屏幕上。
22. **判断内存泄漏必须做"迭代翻倍"对比**。看到私有内存涨了 80MB 就下结论会误判——
    把迭代从 30 次加到 60 次再跑一遍：增量跟着翻倍才是泄漏，增量几乎不变就是一次性高水位。
    配合 GDI/USER 对象计数一起看，比单看内存可靠得多。
23. **遮罩显示后必须重新抬一次顶层**。别的置顶窗口（悬浮播放器、悬浮工具、自检探针）会插进顶层带，
    把遮罩压在下面——表现为"截图时某些区域没被压暗，甚至能看到别人的窗口"。
    用 `SetWindowPos(HWND_TOPMOST, SWP_NOMOVE|SWP_NOSIZE|SWP_NOACTIVATE)` 在显示之后再抬一次。
24. **自动化 GUI 自检会被真实鼠标覆盖**。遮罩一出现，WPF 会派发一次鼠标移动，
    80ms 防抖后按真实光标位置重新解析吸附，把程序摆好的高亮改掉。
    自检需要能关掉指针跟踪的开关（`HoverTrackingEnabled`）。反过来看，这个"冲突"恰好证明真实事件链路是通的。
25. **"预览与导出像素一致"靠两条硬约定**：① 标注坐标、线宽、字号全部用**物理像素**，不用 DIP；
    ② 导出时用 `RenderTargetBitmap(96dpi, 选区物理像素)` 1:1 渲染，屏幕渲染则推一个 `1/缩放` 的矩阵。
    两条任缺一条，就会出现"屏幕上箭头很粗、导出后细一圈"的经典问题。
26. **马赛克不要依赖图像插值**。`TransformedBitmap` + 最近邻在 `RenderTargetBitmap` 下会退化成双线性，
    结果是"打了一层模糊"而不是"像素块"——而且这种错误在截图上看着还挺像回事。
    确定性做法：读出区域像素，按块取平均色，**逐块画矩形**，完全不经过插值。
27. **别在纯色背景上验证视觉效果**。第一次测马赛克时区域选在白底空白处，
    "像素化了"和"根本没画"在数字上几乎一样，白跑一轮。
    验证渲染类功能一定要选**内容有变化**的区域，并同时断言"块内一致"和"与原图有差异"两条。
    如果断言依赖屏幕内容，而屏幕内容每次运行都在变（比如截图里是一个聊天窗口），
    最终一定会变成随机失败——改成**合成底图**（例如棋盘格）做断言，真实屏幕只负责验证链路能跑通。
28. **矩形的"内缩/外扩"语义要写死**。第一版工具栏写了个 `Inflate(rect, amount)`，
    实际语义是"内缩 amount"，但图标绘制传了 `-9` 想内缩，结果把图标画进了 50×50 的框里、
    盖到相邻按钮上——表现就是"工具栏大小不统一、图标互相重叠"。
    现在拆成 `Inset`（正值收缩）与 `Expand`（正值外扩）两个名字，
    并在自检里断言"所有按钮同尺寸"，杜绝这类回归。
29. **默认值不要写死在绘制/创建分支里**。荧光笔曾经在创建标注时硬编码黄色，
    用户在工具栏选了别的颜色完全无效——这是"看起来功能有、其实没接上"的典型。
    凡是能通过界面改的样式（颜色、宽度、字号），创建标注时必须从**同一份会话状态**读取，
    并补一条状态断言（例：选蓝 → 荧光笔的 `A=102, RGB=10,132,255`）。
30. **图标不要靠"凑形状"**。画笔图标最初是"斜线 + 三角笔尖"，在 16×16 里看起来就是个箭头，
    和箭头工具撞脸。小尺寸图标要选**轮廓特征明确**的形状（曲线 vs 直线），
    不要指望用户能分辨细节差异。
31. **图标要按"统一规格"画，而不是各自调**。最终定下的规则：
    内容画在 14×14 内容框内；带箭头的图标（箭头/撤销/重做）共用同一组头部尺寸（6.2×2.9）；
    对角线图标（箭头/直线）要略超出内容框，否则视觉上比方形图标小一圈；
    撤销/重做用"单一曲线 + 实心箭头"，不要再拼"弧 + 尾巴 + 三角"三段——小尺寸下会散架。
32. **无边框窗口的"边框"要画，不要用 Border 厚度**。贴图窗口如果给 `Border` 设 `BorderThickness=1`，
    内容区会被挤小 2 DIP，100% 缩放就不再是 1:1，图片会被轻微重采样。
    正确做法：`Grid` 里叠一个 `IsHitTestVisible=false` 的 `Rectangle` 描边，布局不受影响。
33. **贴图的尺寸换算与遮罩同一套**：物理像素 ÷ 显示缩放 = DIP。100% 缩放时窗口 DIP 尺寸
    = 图片像素 ÷ 缩放，屏幕上正好 1:1；改缩放时只改窗口尺寸，图片始终按窗口拉伸。
    缩放要以**光标为锚点**反推窗口左上角（`Left -= anchor.X * (ratio - 1)`），否则放大时内容会跑偏。
34. **滚轮事件发给"有焦点的窗口"，不是光标下的窗口**。贴图如果 `ShowActivated=false`，
    用户滚轮会完全没反应（我在自检里用真实输入注入才复现出来）。
    另外**精准触控板的双指捏合会合成 `Ctrl+滚轮`**——所以透明度快捷键要用 `Alt+滚轮`，
    用 `Ctrl+滚轮` 会让笔记本用户一捏合就变成调透明度，表现为"滚轮行为完全不对"。
35. **无边框窗口拖动别自己算 Left/Top**。手动累加会和高 DPI 取整打架，拖起来一顿一顿；
    用 `Window.DragMove()` 交给系统模态移动循环，跟手、平滑、DPI 正确。
36. **点击穿透必须"创建时就是分层窗口"**。`WS_EX_TRANSPARENT` 只有在窗口同时是
    `WS_EX_LAYERED` 时才影响鼠标命中；但给已经创建的 WPF 窗口运行期补 `WS_EX_LAYERED`
    会导致整个窗口不再绘制（内容消失）。正确做法：创建时 `AllowsTransparency=true`，
    运行期只切 `WS_EX_TRANSPARENT` 并跟上 `SWP_FRAMECHANGED`。
    另外**不要**对 WPF 逐像素 alpha 窗口调 `SetLayeredWindowAttributes`——它会把窗口切成
    "整窗 alpha"模式，WPF 的内容同样会消失。
37. **自检要区分"实现错"和"环境不让"**。开机自启写在 `HKCU\Run`，在沙箱/受控环境里
    子进程写注册表会被拒绝；这时应该打印原因并标记"跳过"，而不是让自检假红。
    纯逻辑部分（命令行拼装）照常断言，保证有价值的部分永远可验证。
38. **状态变更必须沿事件链传到底**。贴图开启点击穿透时，`PinWindow` 只改了自己的标志位，
    没有通知 `PinManager`，于是 `AnyClickThrough` 变了但没人转发，托盘里的"取消贴图穿透"
    一直停在启动时的禁用状态——用户看到的就是"按钮不可用"。
    凡是"某处状态 → 某处 UI 可用性"的链路，都要在中间层把事件转发出去（`PinWindow →
    PinManager → App → 托盘`），并给这条链加一条自检断言。
39. **注入式 GUI 测试必须先验前置条件**。`mouse_event` 的滚轮发给**前台窗口**、
    点击发给光标所在窗口；应用在后台时 `SetForegroundWindow` 会被系统拒绝，
    而真人可能随时移动鼠标。之前这些断言时过时不过，就是条件没满足。
    现在自检在注入前检查"前台窗口==贴图 且 光标确实在贴图上"，不满足就**明确跳过**并打印原因，
    确定性断言（标志位、状态通知、尺寸、句柄）仍然照常判红绿。
